# Техника, буровые услуги и простой вход — уточнение портала

Дата: 03.10.2026. Запрос владельца: самостоятельная подача объявлений, подробные релевантные фильтры, вход Google/email и поисковая видимость. Основа — утверждённый показ 13 и закрытая equipment foundation. Новый показ 17 предназначен для согласования уточнённых полей/входа; это не публичный запуск.

## Что реально уже существует

- Новый закрытый API, статусы DRAFT/PENDING_MODERATION/ACTIVE/REJECTED/ARCHIVED, ownership/revision checks, ручное одобрение; безопасный приём и управление фотографиями/cleanup подготовлены отдельными выпусками.
- Google provider в действующем NextAuth config подготовлен за MARKETPLACE_IDENTITY_ENABLED и credentials. Живой пользовательский OAuth пока не проверен; production SQL/flags не включены по журналу. Credentials разрешает только env-admin; POST register возвращает 404. Email provider не реализован.
- `src/lib/equipment-listings/domain.ts`: техника drill/excavator/compressor/transport, услуги drillService/geoService; методы CORE/RC/AUGER. Пока одни depth/diameter, у экскаватора bucket/mass, у компрессора нет pressure/flow.
- `src/lib/data/service-taxonomy.ts` содержит более широкий старый четырёхъязычный справочник. Это источник кандидатов и переводов, не подключённая к новому API схема. В нём смешаны разные оси (керновое/алмазное/направленное) — слепо копировать нельзя.

## Продуктовое решение для согласования

Сохраняем четыре коротких шага показа13: предложение → характеристики/фото → вход и контакты → предпросмотр. Можно начать заполнение без входа; перед серверным сохранением/отправкой нужен подтверждённый аккаунт. Текстовый локальный черновик не должен содержать пароль/OTP/приватные документы; после входа — серверное автосохранение. Файлы загружаются только через уже проверенный авторизованный процесс, не как произвольные URL.

Google — основная кнопка, email — полноценный резервный вход по одноразовой ссылке. Это предлагаемое UX-решение, не обещание доставленного письма. Для китайской аудитории email обязателен как независимый резерв; доступность Google не считать универсальной. Не требовать SMS ради аккаунта, если выбран Google/email; контактный телефон и его отдельная проверка не равны логину. Неподтверждённый телефон не получает значок «подтверждён».

## Категории: предложение, предмет, назначение и метод отдельно

1. Что предлагается: аренда техники / продажа техники / выполнение работ. «С бригадой» и «с оператором» — условие, не новый метод бурения.
2. Техника: буровые установки, экскаваторы/землеройная техника, компрессоры, транспорт. Дополнительные подтипы расширяются в реестре, не размножением URL. Услуги: бурение и геологические работы; бурение описано ниже подробно, другие услуги получают самостоятельную схему позже.
3. Для буровых работ назначение: разведка полезных ископаемых; вода/гидрогеология; инженерные/геотехнические изыскания; взрывные скважины; геотермальные работы; прокладка коммуникаций/ГНБ; другое. Это кандидаты для формы, не утверждение что компания выполняет все работы.
4. Метод получения/проходки: керновое; обратная циркуляция RC; шнековое; роторное без отбора керна; пневмоударное; соник; другое. Конкретные допустимые сочетания проходят предметную вычитку; назначение не определяет метод автоматически. Алмазный инструмент — уточнение кернового, направленность/ориентация — отдельный признак траектории. DTH и RC не объединять как синонимы.

Сервисный справочник не должен обещать «все возможные методы мира»: начать с проверяемого набора, поиска синонимов и «другое — опишите». Публикация нового варианта сначала нормализуется модератором, а не создаёт произвольную категорию.

## Характеристики и фильтры

| Ветка               | Основные параметры                                                                                               | Дополнительные сведения                                                                                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Буровая установка   | марка/модель, методы, ходовая, оператор, место техники                                                           | год/состояние при продаже, масса/габариты, питание, доставка, комплектация                                                            |
| Буровые работы      | назначение, методы, регионы выезда                                                                               | площадка поверхность/подземная, траектория, мобилизация, бригада/оснастка, объём/доступность                                          |
| Возможность бурения | **метод + диаметр скважины (мм) + рабочая глубина (м)** в одной строке; несколько строк на установку/предложение | типоразмер керновой системы отдельным полем; не выдавать диаметр керна за диаметр скважины; условия применения/источник характеристик |
| Экскаватор          | эксплуатационная масса (т), ковш (м³), ходовая                                                                   | оператор, доставка, навесное оборудование                                                                                             |
| Компрессор          | давление (бар), производительность (м³/мин)                                                                      | питание, мобильность, оператор/доставка                                                                                               |
| Транспорт           | тип транспорта, грузоподъёмность (т)                                                                             | регион, доставка/маршруты, водитель                                                                                                   |

Поиск по глубине/диаметру проверяет **одну и ту же строку возможностей**. Нельзя взять глубину 1200 м из одного режима и диаметр 200 мм из другого и объявить установку подходящей для 200 мм × 1200 м. Диапазоны единиц и чисел проверяет сервер; неизвестное значение отсутствует, не равно 0. Возможности не становятся инженерной гарантией; источник — сведения автора/производителя с честной маркировкой.

Основная выдача: что нужно, аренда/продажа/работы, регион, метод для бурения. Дополнительные параметры раскрываются по категории: глубина/диаметр, ходовая, с оператором, давление/подача и т.д. Фильтры/подача используют один версионируемый словарь кодов, единиц и переводов, чтобы не было разницы между сохранённым значением и поиском. Текстовый поиск нормализует кириллицу/латиницу, названия методов и моделей; без обещания распознать любую ошибку.

Цена: сумма + валюта + единица (час/смена/сутки/метр/объект/штука по типу предложения) **или явно «по запросу»**. Для смены — длительность; для цены — что включено, доставка/топливо/оснастка. При «по запросу» числовая цена не обязательна и не записывается 0. Текущую submission schema надо согласовать с этим UX: не требовать бессмысленную единицу/валюту там, где суммы нет. Старые валидные объявления должны сохраняться при миграции.

## Вход и идентичность

- Google OAuth сохраняет существующее правило immutable provider subject, verified email и серверный UUID. Административные полномочия не назначаются новому аккаунту, существующий admin-вход сохраняется.
- Email: одноразовая короткоживущая ссылка, одно использование, rate limit, нейтральный ответ чтобы не раскрывать существование аккаунта, ограниченный redirect. Проверить доставку/ошибки и возврат в черновик, а не только запись токена.
- NextAuth v4 Email provider требует database adapter/token persistence и способ отправки; нельзя просто добавить кнопку к нынешней RPC. Подобрать совместимый service-only adapter/identity boundary, не возвращать Prisma identity и небезопасный password fallback.
- Связывание Google/email — явное подтверждение контроля аккаунтов; совпадение строки email само по себе не основание для склейки.
- На телефоне и во встроенном WeChat-браузере проверить Google ограничения; предусмотреть открытие обычного браузера и рабочий email-путь с сохранением предложения. Доставка писем/расходы/провайдер проверяются отдельно, до обещания готового входа.

## Публикация, поиск и четыре языка

Сначала модерация, затем публичная карточка со стабильным ID/URL, датой обновления и понятным статусом. Нужны редактирование/снятие, актуальность, жалобы и ответственный за очередь. Политика сроков/квот/оплаты и публичные условия утверждаются владельцем, не задаются в этом документе автоматически.

На RU/KZ/EN/ZH переводятся UI, категории, единицы, ошибки и письма. Исходное описание хранится отдельно; машинный/непроверенный перевод не является утверждённым исходником. Hreflang только для реально доступных версий; технические характеристики не меняются при смене языка.

Индексируемые страницы: опубликованная карточка и содержательные категории с реальными объявлениями. Sitemap, metadata, canonical, внутренние ссылки и соответствующая видимым фактам schema — в выпуске публичной витрины. Черновики, кабинет и private API закрыты; произвольные комбинации фильтров/сортировок не создают тысячи индексируемых дублей. canonical сам по себе не решает crawl explosion; спроектировать отдельную политику параметров/обхода. Не обещать гарантированную индексацию или рекомендации LLM. Для архивов/удалений — честные статусы и 404/410 по утверждённой политике, не массовый redirect на главную.

Сторонние участки — отдельный будущий процесс прав/полномочий. Equipment schema не изменяет `leads`/`lead_private` и не позволяет пользователям публиковать геобазу.

- Server TDD: валидные/невалидные комбинации, совместимые единицы, price-on-request, миграция версии; чужие объекты/файлы недоступны; stale moderation rejected.
- Search TDD: связанная строка возможности, единицы/метод/регион, неизвестные значения, стабильная пагинация/allowlist sort, отсутствие private/contact leakage.
- Auth: настоящий Google и email → одна identity → черновик → фото → submit → approve → публичная карточка → edit/remoderate → archive. Доставка email, защита от повторного токена/смешивания аккаунтов и сохранение admin проверены.

## Реализованный закрытый контракт, 03.10

Исходный аудит выше описывает состояние до этой реализации. Теперь `taxonomy.ts` и `domain.ts` принимают явную v2: до 12 связанных возможностей; CORE/RC/AUGER/ROTARY/DTH/SONIC/OTHER, назначение, площадка и траектория; ходовая, оператор/доставка, pressure/flow/payload, год/состояние для продажи. Неизвестные параметры можно пропустить; пустой массив возможностей и строки без метода отклоняются. V1 продолжает действовать с прежними ограничениями. Переход v1→v2 явный, старые плоские параметры удаляются явно; обратного понижения нет.

Поиск проверяет заявленную глубину **не меньше** запроса при **точно указанном диаметре скважины** в одной строке; типоразмер керновой системы также проверяется в этой строке CORE. Более крупный диаметр не считается доказательством возможности на меньшем. Дополнительные характеристики — заявленные авторами значения, не результаты независимой инженерной проверки. При сортировке цен нужны одинаковые валюта/единица, для смены также длительность; автоматического обменного курса/пересчёта нет.

`/api/equipment-catalog` закрыт, пока оба `EQUIPMENT_MARKETPLACE_ENABLED` и `EQUIPMENT_CATALOG_ENABLED` не равны `true`. Запросы ограничены, приватные поля не участвуют в поиске и не выходят через HTTP. SQL RPC доступен только service_role; миграция подготовлена и проверена на локальных синтетических данных, не применена к production.

Показ 17 ещё ожидает решения владельца. Публичный запуск, Google/email и сквозная форма этим контрактом не подтверждены.
