# Закрытый приём фотографий техники

Продолжение утверждённой закрытой основы из `2026-09-29-marketplace-foundation.md`.
Публичные маршруты, форма, регистрация и production-БД остаются закрытыми.

## Контракт

- POST `/api/equipment-listings/[id]/images`: одна фотография в бинарном теле;
  `Content-Type` JPEG/PNG/WebP, `X-Listing-Revision` — положительная ревизия.
  ID и UUID владельца берём из действующей NextAuth-сессии. Exact Origin из
  настроенного NEXTAUTH_URL/SITE_URL обязателен; cross-site запрещён.
- GET этого маршрута возвращает только безопасные метаданные собственных фото.
  GET `/images/[imageId]` отдаёт собственную обработанную фотографию. Все ответы
  private/no-store/noindex; анонимного чтения и подписанных публичных ссылок нет.
- Флаг EQUIPMENT_MARKETPLACE_ENABLED по умолчанию off:404 до auth/storage.
  Владелец другого объявления получает404. Архив не принимает новые фото.
- Вход до3MiB, потоковый предел независимо от Content-Length; JPEG/PNG/WebP
  подтверждаются сигнатурой и декодированием sharp. Не принимаем SVG, документы,
  анимацию, имена файлов, внешние URL или выбранный пользователем storage path.
- До24млн пикселей, строгое декодирование, timeout; ориентация EXIF учитывается,
  метаданные не переносятся. Производная WebP82, вписана в1600×1600 без увеличения,
  до3MiB. Sharp0.34.3 добавляется явной зависимостью (уже есть транзитивно).
- До8фото на объявление. UUID имени генерирует сервер; приватный бакет
  `equipment-images`, путь `<listing UUID>/<image UUID>.webp`.
- SQL attach RPC под service_role блокирует строку объявления, сверяет владельца,
  ревизию и статус, атомарно проверяет лимит/вставляет метаданные/повышает revision
  и пишет событие. ACTIVE при изменении фото становится PENDING_MODERATION;
  pending-правка инвалидирует старое решение модератора. Порядок0–7 назначает БД.
- На storage.objects отдельная restrictive policy исключает доступ к этому
  бакету anon/authenticated даже при наличии чужих широких permissive policies.
  Таблица изображений и RPC также только service_role. Миграция проверяется
  в изолированной локальной PostgreSQL, не применяется к production.
- При подтверждённом SQL rollback непривязанный объект удаляется после проверки
  отсутствия attachment. При transport error или невалидном ответе RPC не удаляем
  объект даже при пустом SELECT: транзакция ещё может завершиться позднее.
  Неопределённый исход оставляет приватный объект для последующей сверки;
  публичная утечка исключена. Плановая очистка/retention и
  удаление/перестановка фото — отдельный этап до запуска.

## Доказательство готовности этого этапа

TDD: закрытый флаг, UUID/auth/ownership, origin, сигнатура/MIME/реальное декодирование,
тело/пиксели/анимация/metadata, revision/count гонки, rollback, приватные проекции,
успешный upload/read и cleanup/ambiguous commit. Прямые роли БД не читают/пишут
таблицы/бакет/RPC. Точечный и полный Jest с baseline, ESLint/build, независимое
сильное ревью, закрытые локальные и живые HTTP-ответы после обычного pushmaster.
UI не меняется: повторение визуальной матрицы не доказывает этот server-only этап.

## Первичные технические источники (проверены30.09.2026)

- [Vercel request/response payload4.5MB](https://vercel.com/docs/functions/limitations#request-body-size):
  поэтому proxy принимает3MiB, не заявляет поддержку оригинала6MiB.
- [Sharp constructor](https://sharp.pixelplumbing.com/api-constructor/): failOn warning,
  limitInputPixels, по умолчанию включённые ограничения.
- [Supabase Storage RLS](https://supabase.com/docs/guides/storage/security/access-control):
  service key работает отдельно от browser policies; публичный upload не используется.

Это реализация технической границы, не запуск кабинетов, не готовый процесс модерации
фото и не обещание будущего роста трафика.
