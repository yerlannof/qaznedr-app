## Пакет A — достоверные обращения, следующий технический шаг

До реализации отдельная узкая спецификация:

1. В доступных кабинетах проверить возможность связать контактные события с источником/посадочной. Не дублировать уже имеющиеся provider session dimensions.
2. Использовать существующие записи inquiries как факт сохранённой формы; подготовить агрегат за период с исключением явно помеченных QA. Админка уже имеет source_path/UTM и стадии NEW/CONTACTED/MEETING/DEAL/REJECTED. Учесть limit(200) текущего API: не считать длину списка полным итогом, для отчёта предусмотреть точный подсчёт или пагинацию. Клиентский inquiry_submit не равен вставке. Ответ антиспама/успеха не менять; новый внешний event только при доказанной необходимости и действующем согласии.
3. Сверить доступность обработки входящих: админка, ответственный, фактическое уведомление. Проверка доставки с тестовой заявкой/сообщением только в разрешённом тестовом потоке; не загрязнять production ради счётчика.
4. Использовать существующие стадии админки и рабочий журнал команды. Для прямых WhatsApp/WeChat-разговоров сначала выяснить, где команда уже фиксирует результат, затем согласовать только недостающее. Не создавать параллельную CRM и не передавать имена/контакты внешним счётчикам.

Кандидатные пути для отчёта: src/app/api/admin/inquiries/route.ts, src/app/[locale]/admin/inquiries/page.tsx, src/lib/inquiries/ и соответствующие src/__tests__. Публичную форму/API приёма без отдельного подтверждённого дефекта не менять. Это план, не разрешение субагенту менять любые файлы: точные пути и границы ведущий задаёт перед выполнением.

Готово, когда: агрегат совпадает с сохранёнными нетестовыми записями за период, включая выборку более 200 строк; границы дат и исключение QA покрыты тестами; клиентский антиспам-success не считается заявкой; клики мессенджера не названы лидами; используются существующие стадии и проверяемая обработка. Для поведения TDD, полный регресс/сборка и браузер по AGENTS, затем сильное ревью и production smoke.

## Пакет B — доказательства на существующих коммерческих страницах

1. Собрать от владельца разрешённые профили геологов, кейс и подтверждённые реквизиты. Не пересылать документы и не заполнять их догадками.
2. Подготовить полный текст дополнений к services/geological, foreign-investor guide, gold/copper hubs; исключить дублирование нынешнего about и гайда due diligence.
3. Для каждого блока явно показать «уже есть → чего не хватает → точный предлагаемый текст». Новую композицию показать по docs/design/AGENTS.md. Одно предметное согласование готового пакета.
4. После «да» — RU/KZ/EN/ZH, экспертная вычитка терминов, metadata только по содержанию, source/date, CTA с кодом/темой, обычные проверки и выпуск.

Готово, когда инвестор может понять тип предложения, ограничения данных, кто отвечает за оценку, что обсуждать на первом контакте. Влияние оценивается по целевым разговорам, не количеству добавленных слов.

## Пакет C — дистрибуция и китайский путь

1. Взять существующий план китайских кабинетов, не повторять неудачные SMS или отправленные письма.
2. Проверить доступность ZH-пути из реальных материковых сетей; только затем выбирать техническое ускорение при доказанной проблеме.
3. Подготовить один оригинальный материал из согласованного кейса/гайда для доступного профильного канала. Проверить текущие условия, права публикации и релевантность аудитории. Публичный текст/отправку согласовать по действующей области разрешений.
4. Первый Bing AI Performance проверен: 0 цитирований за 31.08–29.09. Повторить позже за завершённый период; Search Performance проверить после подготовки данных (кабинет просит 48 часов). Продолжить регулярный срез коммерческих небрандовых запросов без частого опроса неизменного кабинета.

Готово, когда есть проверенная публикация/профиль, рабочая ссылка на подходящий язык и страница, измеряемые переходы либо честно зафиксированное отсутствие данных. Созданный аккаунт без материала не закрывает задачу.
