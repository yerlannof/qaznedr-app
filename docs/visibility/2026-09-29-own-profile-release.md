# Собственный профиль — закрытая серверная часть

Дата:29.09.2026. Основа:b3f6bfd; UI и публичная регистрация не открываются.

## Сделано

GET/PUT `/api/profile` и POST `/api/profile/setup` переведены на один handler, строгие схемы и server-only repository. Источник ID — UUID текущей NextAuth session. Нет email lookup, клиентского owner ID, insert или upsert. Ошибки доступа/ввода/хранилища разделены; подробности БД не уходят наружу. Каждый ответ private/no-store/noindex. По умолчанию маршруты404 до auth и БД.

Мутации проверяют настроенный exact Origin, cross-site, JSON, строгий UTF-8 и реальный потоковый предел16KiB. Разрешены только имя, компания, контакт, место, сайт, описание, тип профиля/услуг с пределами длины. ID/email/роли/проверки/аватар не меняются. Ответ ограничен собственными полями; служебные поля исключены и SQL select, и выходной схемой. Повторное сохранение одного поля использует обычную семантику последней записи; непереданные поля не перезаписываются.

## Оставшиеся обращения к profiles

- Новые own-profile и admin helpers используют service_role с серверной сессией; массовой подмены anon-клиента не делали.
- `src/lib/supabase/profiles.ts` остался только для legacy listing trust-read; `createProfile`, `updateProfile`, `hasProfileSetup` больше не вызываются действующими profile routes. Legacy объявления не относятся к новому equipment API.
- `/api/investors` делает anon-чтение профилей; `/api/contact-view` пишет старый счётчик через anon. До публичного запуска их нужно закрыть либо заменить отдельным утверждённым публичным контрактом; нельзя давать им service_role для обхода новых запретов.
- `MessagingSystem` содержит прямой browser profile read внутри фактически отключённого списка conversations. Его не включать; нужен отдельный публичный минимум по разрешениям беседы.
- Admin users/stats/moderation и middleware role используют service client за role-check. В legacy dashboard старое чтение `{profile}` обработано как голый объект; при замене UI не переносить этот дефект.
