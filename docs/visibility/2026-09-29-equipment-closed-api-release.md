# Закрытая серверная часть техники и услуг

## Реализовано

- Семь действий владельца/модератора через отдельные маршруты equipment-listings: список/черновик, чтение/редактирование, отправка, архив, очередь и решение модератора. ID владельца берётся из действующей NextAuth-сессии; роль модератора — существующий requireAdmin.
- Флаг EQUIPMENT_MARKETPLACE_ENABLED не задан или не равен true →404 до сессии и БД. В production его не включали. Публичного API и навигации нет.
- Запись требует JSON, точный origin из NEXTAUTH_URL/SITE_URL, тело до32КиБ и expectedRevision. Ошибки БД не раскрываются, ответы private/no-store/noindex. Чужой объект404, устаревшая версия409.
- Новая миграция equipment_listings + equipment_moderation_events: только service_role; прямые SELECT/UPDATE/RPC anon/authenticated запрещены. RPC блокирует строку, сравнивает owner/status/revision и записывает изменение с событием в одной транзакции. Причина отказа сохраняется в истории.
- Архив может содержать неполный черновик. ACTIVE/PENDING всё ещё требуют полной submission-схемы. JSONB ограничен64КиБ, чтобы байтовая длина китайского текста не противоречила разрешённым полям.
- Устаревший POST /api/auth/register теперь всегда404. Удалены Prisma-регистрация и автоматическое назначение первого пользователя super_admin. Существующий вход не менялся.

## Доказательства

- TDD API: отсутствующие маршруты → реализация;33/33 focused (17 API,6 repository,10 domain). Репозиторий сначала4/4, затем два красных теста выявили невозможность архива неполного черновика; исправление дало6/6.
- Полный Jest:1803 pass/28 known failures;79/85 suites. Пять прежних legacy-наборов плюс нестабильное CSRF timing. Новых падений нет.
- TypeScript, ESLint, форматирование и production build прошли. Сборка обнаружила несовместимый optional context в Next route exports; заменено явными типизированными обёртками, повторная сборка зелёная.
- Миграция и scripts/test-equipment-foundation.sql проверены в отдельной локальной PostgreSQL БД. Проверены запрет ролям SELECT/UPDATE/RPC, stale-версия, отсутствие лишнего события, сохранение причины отказа. Сравнение причины использует IS DISTINCT FROM и ловит NULL.
- Ведущий отдельно запустил две конкурентные транзакции: владелец держит row lock и обновляет pending2→pending3; параллельное одобрение старой версии отклонено, итог pending/revision3 и ровно одно событие.
- На production-сборке localhost3107 девять HTTP-проверок всех методов/семейств маршрутов и старой регистрации вернули404+no-store. Browser Use заблокировал открытие API как ERR_BLOCKED_BY_CLIENT; не выдаём это за браузерный pass. UI не менялся, проверки выполнены напрямую по HTTP.
- Независимое сильное ревью Ready после исправления ARCHIVED; финальные типизированные обёртки повторно просмотрены.

## Продолжение и пределы

Миграция проверена локально, **не применена к production**. API выключен, новых пользователей/объявлений/платных сервисов нет. Схема пользователей ещё не унифицирована; этот выпуск не утверждает успешный registration→login. Старые308 и leads/lead_private сохранены.

Далее: отдельный проверенный процесс идентификации и создания профиля в одном хранилище (старый anon-read password fallback не использовать), затем безопасный приём фотографий, утверждённая форма и экран модератора. Перед включением: полноценный lifecycle с реальным хранилищем через HTTP, rate limits/квоты, выбранный вход/SMS при необходимости, условия публикации, ответственный модератор. Не включать флаг только ради демонстрации.

Выпуск — обычный git push master; успешный CI/Production и закрытые HTTP-ответы на публичном домене проверяются после push. Код и миграция разделены: выпуск кода не применяет SQL автоматически.
